# 용어집과 장애 이력

이 문서는 팀 안에서 쓰는 용어의 정확한 뜻과, 청구 시스템에서 일어난 장애와 그 뒤에 정한 규칙을 적는다.
다른 문서가 "INC-2024-03"처럼 참조하는 사건은 여기에 있다.

## 1. 용어

| 용어 | 뜻 | 주의 |
|---|---|---|
| 계정(account) | 청구 단위. 사업자등록번호 하나에 계정 하나 | 워크스페이스와 다르다 |
| 워크스페이스(workspace) | 제품 안의 협업 공간. 계정 하나에 여러 개 가능 | 청구는 워크스페이스가 아니라 계정에 붙는다 |
| 고객(customer) | 계약 주체인 법인. CRM의 단위 | 코드에서는 쓰지 않는다. 계정으로 부른다 |
| 멤버(member) | 워크스페이스에 초대된 사용자 | 좌석 집계의 대상 |
| 좌석(seat) | 플랜이 허용하는 사용자 수 | 레거시는 초대 기준, 현행은 활성 기준(`plans-and-legacy-contracts.md`) |
| 앵커(anchorDay) | 매달 청구 주기가 시작하는 날짜(1~28) | 29~31은 없다 |
| 주기(cycle) | 앵커부터 다음 앵커 전날까지 | 반개구간 `[start, end)` |
| 일할(proration) | 주기 일부에 대한 요금 계산 | 업그레이드에만 한다. 다운그레이드는 이연 |
| 레거시(legacy) | 2021년 개편 이전의 서면 계약 플랜. `L-` 접두 | 삭제 금지, 신규 배정 금지 |
| 크레딧(credit) | 장애 보상으로 지급하는 차감액 | 환불 불가, 6개월 소멸 |
| 공급가액 | 부가세를 뺀 금액. `subtotal` | 쿠폰과 크레딧은 여기에 적용 |
| 세액 | 부가세. `vat` | 공급가액의 10%, 원 미만 절사 |
| 수정세금계산서 | 발행된 세금계산서를 고치기 위해 새로 발행하는 세금계산서 | 삭제 대신 쓴다 |
| PG | 결제 대행사. PayKo | 한 곳만 쓴다 |
| 멱등키 | 같은 요청을 두 번 처리하지 않게 하는 키 | 재시도 시 재사용 |

- "환불"과 "크레딧"을 섞어 쓰지 않는다. 환불은 돈이 나가는 것이고 재무팀 승인이 필요하다. 크레딧은 다음 청구에서 빼는 것이다.
- "취소"는 청구서 취소(수정세금계산서)와 결제 취소(PayKo `CANCELED`)가 다르다. 문맥을 밝혀 쓴다.

## 2. 장애 이력

| ID | 시기 | 무슨 일 | 영향 | 그 뒤 정한 규칙 |
|---|---|---|---|---|
| INC-2022-11 | 2022.11 | 다운그레이드 즉시 일할 계산으로 음수 청구서 발생 | 수정세금계산서 140건, 월 마감 8일 지연 | 다운그레이드는 다음 주기 이연, 환불 없음. 시스템은 음수 청구서를 만들지 않는다 |
| INC-2023-06 | 2023.06 | 청구 배치가 UTC 날짜로 주기를 계산해 KST 새벽 청구가 전날로 잡힘. 같은 달 6시간 장애 | 청구서 작성일자 오류 300여 건, 장애 보상 크레딧 1,850건 | 청구 날짜는 KST 달력 날짜 문자열. 장애 보상은 크레딧으로 |
| INC-2024-03 | 2024.03 | PayKo 타임아웃 뒤 멱등키 없이 재시도해 이중 결제 | 27개 계정 이중 결제, 환불과 공지 2주 | 재시도는 같은 멱등키로. 타임아웃은 성공일 수 있다 |
| INC-2024-05 | 2024.05 | CS 도구에서 거절된 카드에 반복 결제 시도. PayKo 가맹점 경고 1회 | 경고 누적 시 결제 정지 위험 | 거절 코드에는 재시도하지 않는다. CS 도구에서 재시도 버튼 제거 |
| INC-2025-01 | 2025.01 | "안 쓰는 플랜 정리"로 레거시 플랜 레코드 삭제 | 61개 계정 청구 배치 실패 | 레거시 플랜은 숨기되 삭제하지 않는다 |

### 2.1 INC-2024-03 상세

- 3월 14일 09:00 배치에서 PayKo가 카드사 응답 지연으로 `GATEWAY_TIMEOUT`을 돌려줬다. 배치는 실패로 보고 즉시 재시도했다.
- 재시도 요청에 멱등키가 없어 PayKo는 새 결제를 만들었다. 첫 요청도 카드사에서는 승인돼 있었다.
- 27개 계정이 두 번 결제됐고, 정산 대사에서 발견될 때까지 이틀이 걸렸다.
- 교훈: 타임아웃은 "실패"가 아니라 "모름"이다. 모르는 상태에서 다시 보내려면 PG가 중복을 걸러줄 수 있는 키가 있어야 한다.

## 3. 담당

| 영역 | 담당 |
|---|---|
| 청구 정책(플랜 변경, 일할, 쿠폰 한도) | 재무팀 + 제품 정책 담당 |
| 세금계산서 발행, 대사 | 재무팀 |
| PayKo 연동, 장애 대응 | 결제 담당 엔지니어 |
| 레거시 계약 고객 응대 | CS 리드 |

## 4. 변경 절차

- 청구 금액이 달라질 수 있는 변경(일할, 쿠폰, 부가세, 플랜)은 **재무팀 리뷰**를 받은 뒤 배포한다.
- 매달 **1일~7일**과 **말일**에는 청구 로직을 배포하지 않는다. 세금계산서 일괄 발행 기간이고, 문제가 생기면 발행 기한(다음 달 10일)을 못 지킨다.
- 금액 계산을 바꾸면 최근 3개월 청구서로 재계산 비교를 돌려 차이 목록을 재무팀에 보낸다.
- 새 오류 상황을 추가하면 CS가 볼 수 있는 메시지와 대응 절차를 사내 위키에 같이 적는다.

## 5. 배치 운영

- 청구 배치는 매일 KST 09:00에 돌고, 그날이 앵커인 계정을 처리한다. `pendingPlanId` 반영 → 청구서 생성 → 결제 순서다.
- 결제까지 실패한 계정은 다음 날 09:00에 한 번 더 시도한다. 이틀 연속 실패하면 CS에 알림이 가고 계정은 7일 유예 뒤 읽기 전용이 된다.
- 배치 결과는 `#billing-batch` 채널에 요약이 올라간다. 실패 0건이 아니면 결제 담당 엔지니어가 그날 확인한다.
- 배치가 아예 돌지 않은 날은 다음 날 배치가 이틀치를 처리한다. 앵커가 전날인 계정의 청구서 작성일자는 **원래 앵커 날짜**로 한다.

## 6. 계정 필드 요약

청구 로직이 읽는 계정 필드는 다음과 같다. 전체 스키마는 `account-service`에 있다.

| 필드 | 타입 | 뜻 |
|---|---|---|
| `id` | string | 계정 ID |
| `businessNumber` | string | 사업자등록번호. 쿠폰 중복 사용 판단 기준 |
| `planId` | string \| null | 현재 플랜. Enterprise는 `null` |
| `pendingPlanId` | string \| null | 다음 주기부터 적용될 플랜 |
| `anchorDay` | number | 1~28 |
| `credits` | number | 잔여 크레딧(원) |
| `contractRef` | string \| null | 레거시 계약 번호 |
| `overseas` | boolean | 해외 법인 증빙 등록 여부. 영세율 판단 기준 |
| `cancelAt` | string \| null | 해지 예약된 주기 종료일 |

## 8. 구현할 때 자주 틀리는 것

- "고객"이라는 이름의 변수나 테이블을 새로 만드는 것. 청구 단위는 계정이다.
- 워크스페이스 ID로 청구서를 만드는 것. 계정 ID로 만든다.
- 장애 보상을 환불로 처리하는 것. 크레딧이다.
- 배치를 하루 건너뛴 뒤 작성일자를 실제 실행일로 쓰는 것. 원래 앵커 날짜다.
- 1~7일이나 말일에 청구 로직을 배포하는 것.
