# PG(PayKo) 연동 계약과 운영 주의점

결제는 PayKo 한 곳을 쓴다. `src/payment.js`의 `charge`는 PayKo `/v1/payments`를 부르는 얇은 함수다.
PayKo API의 동작 방식, 계약상 제약, 과거에 겪은 문제는 코드에 없다. 이 문서가 그것을 적는다.

## 1. 계약 개요

- 계약: 2022년 3월 체결. 카드, 가상계좌, 계좌이체 세 가지 수단.
- 수수료: 카드 2.3%, 가상계좌 건당 300원, 계좌이체 1.5%.
- 정산: D+2 영업일. 정산 내역은 매일 06:00에 SFTP로 받고, 재무팀이 청구서와 대사한다.
- PayKo 담당자 채널과 장애 연락처는 사내 위키 "결제/PayKo"에 있다. 이 문서에는 적지 않는다.

## 2. API 동작 특성

### 2.1 멱등키(`Idempotency-Key` 헤더)

- 요청에 `Idempotency-Key` 헤더가 있으면 PayKo는 **24시간 동안 같은 키의 요청에 첫 번째 응답을 그대로 돌려준다.**
  결제를 두 번 만들지 않는다.
- 헤더가 없으면 요청마다 새 결제가 만들어진다. `orderId`가 같아도 막아주지 않는다(`DUPLICATE_ORDER`는 결제가
  `DONE`된 뒤에만 난다. 진행 중 상태에서는 두 건이 모두 통과할 수 있다).
- 키는 요청마다 새로 만들되, **같은 결제를 다시 시도할 때는 반드시 같은 키를 다시 보낸다.** 재시도마다 새 키를 만들면
  멱등키가 없는 것과 같다.
- 2024년 3월 이중 결제 사고(INC-2024-03)의 원인이 바로 이것이다. 타임아웃 뒤 재시도했는데 키가 없어서 고객 27곳이
  두 번 결제됐다. 환불과 사과 공지에 2주가 걸렸다.

### 2.2 오류 코드와 재시도 가능 여부

| 분류 | 코드 | 의미 | 재시도 |
|---|---|---|---|
| 일시 오류 | `NETWORK_ERROR` | 연결 실패 | 가능 |
| 일시 오류 | `GATEWAY_TIMEOUT` | PayKo가 카드사 응답을 못 받음. **결제가 성공했을 수도 있다** | 같은 멱등키로만 가능 |
| 일시 오류 | `PROVIDER_UNAVAILABLE` | 카드사 점검 | 가능 |
| 한도 | `RATE_LIMITED` | 초당 요청 한도 초과 | 2초 뒤 가능 |
| 거절 | `DECLINED` | 카드사 거절 | **금지** |
| 거절 | `INSUFFICIENT_FUNDS` | 한도 초과, 잔액 부족 | **금지** |
| 거절 | `INVALID_CARD` | 카드 정보 오류, 만료 | **금지** |
| 거절 | `FRAUD_SUSPECTED` | 이상거래 탐지 | **금지**. 즉시 CS 에스컬레이션 |
| 중복 | `DUPLICATE_ORDER` | 같은 `orderId`로 이미 `DONE` | 금지. 기존 결제를 조회한다 |

- 거절 코드에 재시도하면 카드사 이상거래 탐지에 걸린다. PayKo는 가맹점 단위로 "거절 후 재시도" 비율을 보고,
  기준을 넘으면 경고를 보내며 세 번째 경고에서 결제를 정지한다. 2024년 5월에 첫 경고를 받았다(INC-2024-05).
  당시 원인은 CS 도구에서 사람이 "다시 결제"를 반복 클릭한 것이었지만, 자동 재시도도 같은 기준으로 집계된다.
- `GATEWAY_TIMEOUT`은 결제가 실제로는 성공했을 수 있다. 같은 멱등키로 재시도하면 성공한 결제의 응답이 돌아오고,
  다른 키로 재시도하면 이중 결제가 된다.

### 2.3 재시도 횟수와 간격

- PayKo 연동 가이드: 일시 오류는 **최대 3회, 간격 2초 이상**. 그 이상은 `RATE_LIMITED`로 막힌다.
- 모든 시도가 실패하면 결제 실패로 기록하고, 청구 배치는 다음 날 09:00에 한 번 더 시도한다(배치 재시도는 별도 시스템).

### 2.4 결제 상태

| 상태 | 의미 |
|---|---|
| `DONE` | 결제 완료 |
| `WAITING_FOR_DEPOSIT` | 가상계좌 발급됨, 입금 대기. **실패가 아니다** |
| `CANCELED` | 취소됨 |
| `EXPIRED` | 가상계좌 입금 기한(3일) 경과 |

- 가상계좌는 요청 응답이 `WAITING_FOR_DEPOSIT`으로 오고, 입금되면 웹훅으로 `DONE`이 온다. 요청 응답만 보고
  실패 처리하면 안 된다.

## 3. 요청 규칙

- `orderId`: 최대 64자, 영숫자와 `_`, `-`. 가맹점 안에서 유일해야 한다. 청구서 번호를 그대로 쓴다.
- `amount`: KRW 정수. 카드 결제는 100원 미만이면 `INVALID_AMOUNT`. 0원 청구서는 PayKo를 부르지 않는다.
- `currency`: 항상 `KRW`. 다른 통화는 계약에 없다.
- 카드 결제 500만 원 초과 건은 PayKo가 추가 인증을 요구할 수 있다. Enterprise는 카드 결제를 안 하므로 실무에서는 드물다.

## 4. 테스트 환경

- 샌드박스 키는 `pk_test_`로 시작한다. 샌드박스에서는 `amount`가 `1004`이면 `DECLINED`, `5000`이면 `GATEWAY_TIMEOUT`을 돌려준다.
- 단위 테스트에서는 PayKo를 부르지 않고 `gateway` 객체를 가짜로 넣는다. 통합 테스트는 주 1회 샌드박스로 돈다.

## 5. 정산 대사

- 매일 받는 정산 파일의 `paymentKey`를 청구서의 결제 기록과 맞춘다. 맞지 않는 건은 재무팀이 확인한다.
- `paymentKey`는 결제 응답에서 받은 값을 **그대로** 저장한다. 환불, 취소, 대사 모두 이 키로 한다.

## 6. 웹훅

- PayKo는 결제 상태가 바뀔 때 `/webhooks/payko`로 POST한다. 가상계좌 입금(`DONE`), 만료(`EXPIRED`), 취소(`CANCELED`)가 대상이다.
- 요청 헤더의 서명(`PayKo-Signature`)을 검증한다. 검증 실패는 400으로 응답하고 처리하지 않는다.
- PayKo는 2xx를 못 받으면 같은 웹훅을 **최대 5번** 다시 보낸다. 그래서 웹훅 처리는 같은 `paymentKey`와 상태가 두 번 와도
  결과가 같아야 한다.
- 웹훅이 결제 요청 응답보다 먼저 도착한 사례가 있다(카드 결제에서 드물게). `paymentKey`로 결제 기록이 없으면 30초 뒤에 다시 처리한다.

## 7. 취소와 환불

- 취소 API는 `/v1/payments/{paymentKey}/cancel`이다. 부분 취소는 `cancelAmount`로 한다. 취소도 멱등키를 쓴다.
- 취소는 재무팀 승인 뒤에만 부른다. 청구 시스템이 자동으로 취소를 부르는 경우는 **업그레이드 결제가 성공했는데 플랜 변경 저장이 실패한 경우** 하나뿐이다.
- 가상계좌 결제의 환불은 고객 계좌로 송금이라 `refundReceiveAccount`가 필요하다. CS가 고객에게 받아 입력한다.
- 카드 취소는 승인 취소로 처리되고, 정산 뒤(D+2 이후)에는 매입 취소가 되어 고객 카드 명세에 환불로 잡힌다.

## 8. 구현할 때 자주 틀리는 것

- 모든 예외를 재시도하는 것. 거절 코드는 재시도하지 않는다.
- 재시도마다 새 멱등키를 만드는 것. 한 결제 시도 묶음은 키 하나다.
- `GATEWAY_TIMEOUT`을 실패로 확정하는 것. 같은 키로 재시도하거나 조회 API로 확인해야 한다.
- `WAITING_FOR_DEPOSIT`을 실패로 처리하는 것.
- 재시도 간격을 두지 않는 것. 최소 2초, 최대 3회.
- `paymentKey`를 가공해서 저장하는 것. 받은 그대로 저장한다.
- 0원 청구서에 PayKo를 부르는 것. 0원은 결제 없이 `DONE`으로 기록한다.
